# patch v42 — фильтр «Статус менялся за N дней» в реестре сделок Битрикс24

Ставится поверх v41. В фильтре реестра (`/bitrix/deal`, и во вкладке «Сделки Битрикс» карточки партнёра —
это тот же блок) — поле «Статус менялся за, дней»: число дней N и необязательный список статусов «в какой».

Заодно в рабочей копии уже лежит правка 08.10.2026: `has_proposal` по умолчанию `'all'` (все сделки, с КП и без).

## Как работает отбор

Поля фильтра:

- `stage_changed_days` — целое 1…3650 (`STAGE_CHANGED_MAX_DAYS`); пусто, 0, больше 3650 или не число — «не отбирать».
- `stage_changed_to[]` — статусы, в которые был переход. Значения — те же, что у поля «Стадия»:
  **названия** (`crm_deal.stage_name`, список `ProposalDealService::stages()`), а не коды.

Сделка попадает в выборку, если в `crm_deal_stage_history` у неё есть хотя бы одна строка-переход
(`type_id <> 1`, см. ниже), подходящая под оба поля:

```sql
crm_deal.id IN (
    SELECT DISTINCT deal_id FROM crm_deal_stage_history
    WHERE deal_id IS NOT NULL
      AND (type_id IS NULL OR type_id <> 1)                -- создание сделки не считается
      AND date_create >= NOW() - INTERVAL N DAY            -- если задано N
      AND (stage_id IN (коды) OR stage_name IN (названия)) -- если выбраны статусы
)
```

Это один подзапрос в базе Битрикса внутри основного запроса реестра (`CrmDealRegistryService::stageChangedQuery()`),
без запроса на каждую сделку; работают индексы `deal_date` и `date_create`.

- **Статусы без N** — отбор за всё время истории («когда-либо переходила в Completed»).
- **Названия → коды.** В фильтре — названия, в истории переход надёжнее узнавать по коду стадии `stage_id`:
  коды для выбранных названий собираются по `crm_deal` (`DISTINCT stage_id WHERE stage_name IN (…)`);
  дополнительно сверяется `stage_name` строки истории — на случай, если код в зеркале сделок не встретился
  (стадия, в которой сейчас нет ни одной сделки). Сейчас в Битриксе одна воронка (category 0), названия и коды
  стадий один к одному (`UC_05K974` = TCP, `WON` = Completed и т. д.).
- **`type_id`.** Константа `HISTORY_TYPE_CREATE = 1` — по документации BI-коннектора это создание сделки.
  **Сверено на проде 08.10.2026** (1509 строк, 425 сделок): type_id 1 — 425 строк, ровно одна на сделку и всегда самая ранняя; 2 — 886 (промежуточные, semantic P); 3 — 198 (итоговые: S 66, F 132). Пустых type_id нет.
  За 7 / 30 / 90 дней статус менялся у 17 / 34 / 68 сделок; реестр показывает 16 / 33 / 67 — одна сделка создана до 2025-01-01 и видна только с «Все сделки» (с ней 17 / 34 / 68).
  Было указано: значение надо сверить на данных прода: `SELECT type_id, COUNT(*) FROM
  crm_deal_stage_history GROUP BY type_id` — у каждой сделки должна быть ровно одна строка с type_id 1, самая ранняя.
  Строки с пустым `type_id` считаются переходами.
- **Время.** `date_create` сравнивается с «сейчас» по часам приложения (Europe/Moscow). Если BI-коннектор отдаёт
  время в UTC, граница N дней сдвинется на 3 часа — для фильтра в днях это несущественно.
- **Вкладки.** Числа у вкладок («Сделки», «Проекты», «Архив») пользовательский фильтр не учитывают — как и для
  партнёра, менеджера и остальных полей (`counts()` считает то, что вкладка покажет по клику, с чистым отбором).
  Новое поле ведёт себя так же; правок в `counts()` нет.
- **Счётчик «Фильтр (n)»** — дни и статусы считаются отдельными правилами (N=30 и один статус — 2).
- **Выгрузка Excel** берёт отбор из того же `params()`; попап выгрузки передаёт оба поля скрытыми полями,
  адрес попапа после поиска без перезагрузки (`partial=1`) собирается через `query()` и тоже их несёт.

`sql/create_crm_deal_stage_history.sql`. Строка — событие истории стадий сделки из BI-коннектора

не менялся. Пока таблица пустая, фильтр с N или статусами честно отдаёт 0 сделок.

## Дальше

Идея аналитики на той же таблице: **интервал в днях между двумя статусами** по каждой сделке — например,
от первого перехода в TCP до перехода в Contracting или Completed. Для сделки берётся `MIN(date_create)` строки
с первым статусом и `MIN(date_create)` строки со вторым (позже первой), разница в днях — `DATEDIFF`. Это даёт
колонку в реестре/выгрузке («дней от КП до договора») и сводку по менеджерам и партнёрам: медиана и разброс,
сделки, застрявшие дольше обычного. Решить с владельцем: какие пары статусов интересны, как считать возвраты
в статус (первый или последний переход), что делать со сделками, где второго статуса ещё нет (до сегодня или пропуск).
