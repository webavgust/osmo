Нужно сделать API генератора КП OSMOVIEW CP доступным для серверных запросов с портала osmo-avg.ru. Портал будет забирать список КП и детали по каждому КП.

## Что сейчас не так
API сейчас работает по адресу https://ais-pre-c4wikvkthlyf6i4hcrukra-708753304536.europe-west2.run.app — это адрес предпросмотра Google AI Studio. Любой запрос, который приходит не из браузера (curl, PHP, любой сервер), получает 302 на /__cookie_check.html. Дальше идёт перенаправление на aistudio.google.com/applet-auth-bridge, то есть требуется вход в аккаунт Google. До самого приложения запрос не доходит, и ключ x-api-key даже не проверяется. В браузере всё работает только потому, что там уже открыта сессия Google.

## Что сделать
1. Опубликовать backend приложения обычным сервисом Google Cloud Run в своём GCP-проекте (например через «Deploy to Cloud Run» из AI Studio или `gcloud run deploy`), без обвязки AI Studio:
   - доступ без аутентификации Google: `--allow-unauthenticated` (или роль `roles/run.invoker` для `allUsers`);
   - ingress: `all`;
   - на выходе должен получиться постоянный адрес вида `https://<сервис>-<хеш>.<регион>.run.app` (или свой домен), который не редиректит на cookie_check и не требует входа в Google.
2. Проверить, что у сервисного аккаунта Cloud Run есть доступ на чтение к базе с КП (Firestore и т. п.): вне AI Studio доступ к данным может не подхватиться сам.
3. Раз сервис станет публичным, защищать данные должен только API-ключ:
   - все маршруты `/api/cp/*` без верного ключа отвечают `401` с JSON, например `{"success":false,"error":"unauthorized"}`;
   - ключ принимается в заголовке `x-api-key` (как сейчас; `?api_key=` можно оставить);
   - ключ хранится только на сервере (переменная окружения или Secret Manager), не попадает в клиентский бандл и не лежит в репозитории;
   - сравнение ключа — в постоянное время;
   - остальной интерфейс генератора может оставаться за авторизацией — открыть нужно только API.

## Контракт API — не менять
Портал уже написан под текущий формат, поэтому пути, имена полей и обёртку ответа оставить как есть.

- `GET /api/cp/list` → `200`, `Content-Type: application/json`:
  `{"success":true,"count":N,"data":[{"id":"<doc-id>","projectName":"…","customerName":"…","createdAt":"dd.mm.yyyy","updatedAt":"<ISO>","totalCameras":123,"userId":"…"}]}`
- `GET /api/cp/detail/{id}`, где `{id}` — doc-id из списка → `200`:
  `{"success":true,"data":{…полная запись КП…}}`, где `data.id` — номер КП (`AK528`). Поля записи (`items`, `detailedWorks`, `currency`, `exchangeRate`, `isVatIncluded`, скидки, `hardwareRequirements`, `cameraTypes` и т. д.) не переименовывать.
- Ошибки — тоже JSON: `401`/`403` при неверном ключе, `404` если КП не найдено, `500` при сбое. Никогда не отдавать HTML и не отвечать редиректами 3xx: портал считает 3xx и HTML ошибкой.

Желательно, но не обязательно:
- добавить в ответ detail поле `"docId":"<doc-id>"` (сейчас в detail есть только номер AK…, а doc-id — только в списке);
- следить, чтобы `updatedAt` в списке менялся при каждой правке КП: портал по нему понимает, что запись надо перечитать.

## Как проверить перед тем, как отдавать
В командах ниже `<URL>` — новый базовый адрес, `<KEY>` — ключ.

```bash
curl -s -o /dev/null -w "%{http_code}\n" "<URL>/api/cp/list"
```
Должно быть `401`, а не `302`.

```bash
curl -s -H "x-api-key: <KEY>" "<URL>/api/cp/list" | head -c 300
```
Должен прийти JSON `{"success":true,"count":…,"data":[…`.

```bash
curl -s -H "x-api-key: <KEY>" "<URL>/api/cp/detail/<doc-id из списка>" | head -c 300
```
Должен прийти JSON `{"success":true,"data":{"id":"AK…`.

```bash
curl -sI -H "x-api-key: <KEY>" "<URL>/api/cp/list"
```
В заголовках не должно быть `Location` и `__cookie_check`.

- если ключ поменялся — новый ключ, но только защищённым каналом, не в общем чате и не в git.
