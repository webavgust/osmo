# patch-v25 — партия правок владельца от 11.09.2026 + КП без перезагрузки (ТЗ п.6)

Ставится поверх `patch-v24`. Девять правок из списка владельца плюс пункт 6 ТЗ
(список КП без перезагрузки). Скоринг партнёров из той же партии вынесен в
отдельный `patch-v26` — он же итерация 6 плана.

## Что сделано

### 1. Перенос КП из OSMOVIEW CP: дополнительные сборы и все варианты

**Было:** переносился один вариант (тип лицензии выбирался «по большинству»),
`additionalCharges` показывались в предпросмотре справочно и в КП не попадали.

**Вариант — это столбец КП** (тот, что добавляется кнопкой «+» в форме
редактирования, с переключателем «Пилот / Годовая / Безлимит»), а не новая
итерация. Перенос так и делает: одна итерация КП, в ней N столбцов —
по строке в `proposal_variants` на столбец, `is_main` у основного.

**Стало.** В ответе `detail` многовариантного КП дополнительные варианты лежат
под числовыми ключами верхнего уровня (`"0"`, `"1"` …), а основной развёрнут в
корне объекта — так устроен ответ Алексея, проверено на AK904 и AK541.
`OsmoviewCpMapper::variants()` разбирает payload в список вариантов (сначала
числовые ключи по возрастанию, последним корневой). `preview()` показывает все
варианты, `request()` собирает их в формате формы КП: `period`, `period_active`,
`period_value`, `partner_*_discount` — по каждому индексу варианта,
`platform_cell[1][v]`, `cell[i][v]`, `cost[i][v]`, `work_cell[i][v]`.

Позиции общие на КП, ячейки — свои у каждого варианта: сценарии склеиваются по
`scenarioId` (кастомные `"0"` — по названию), работы по id. Позиции, которой в
варианте нет, ставится `active = 0, count = 0` — ровно так же поступает форма,
когда позицию выключают руками.

Дополнительные сборы переносятся в блок «Дополнительные начисления»
(`proposal_variant_extra_pays`) через `ProposalVariantExtraPayService::create()`
для каждого варианта, `type = 'all'`, имя — `description` сбора. Переносятся
только при `taxMode = custom_charges`; при `none` сборы не переносятся, но в
предпросмотре о них написано.

**Одновариантные КП не изменились.** Вывод `preview()` и `request()` старого и
нового маппера сверен по всем 27 записям `external_proposals`: 25 одновариантных
совпали побайтово, отличаются только AK904 и AK541.

Проверено на живом переносе AK541 → КП **AA794**
(`/proposals/edit/76deecc3-9ee7-45d1-8e03-8b05765ed516/1`): одна итерация,
в форме два активных столбца из семи, в базе две строки `proposal_variants`
(`is_main = 1` у первого) с 4 сценариями и 6/5 работами. КП тестовое, осталось
в локальной базе — удалить или оставить, решает владелец.

### 2. Попап проекта: «Срок» только у пилота

Было наоборот — срок показывался, когда «Пилот» снят. Перевёрнуто в четырёх
местах: показ строки в форме, переключатель на клиенте, запись в
`DealProjectService::create()/update()` (у не-пилота срок обнуляется) и вывод в
карточке проекта.

### 3. Карточка партнёра: отбор «есть КП» и фильтр, который не слетает

`PartnerController::TAB_DEFAULTS` — на карточке партнёра «есть КП» по умолчанию
**не важно** (в реестре остаётся «нет»: там выискивают непосчитанные сделки).

Отбор вкладки теперь живёт в адресе страницы, как на самом реестре: после F5
вкладка открывается той же и с тем же фильтром, ссылку можно отправить. Каждая
вкладка помнит свой отбор; при переходе на другую вкладку её фильтр не тащится.

Заодно починено открытие вкладки из адреса: бандл Metronic грузится отдельным
файлом, и `bootstrap.Tab` на момент `ready` мог быть ещё не определён — вкладка
молча не открывалась. Теперь ждём появления `bootstrap.Tab` (как это уже сделано
для select2 в `_filter.blade.php`).

### 4. Создание спецификации: не открывался выбор компании

**Симптом:** клик по полю компании — и ничего, список не показывается.

**Причина.** Тема `bootstrap5` копирует классы исходного `<select>` на «видимое»
поле select2. В этих попапах поля помечены `class="select2"`, поэтому само поле
начинало совпадать с селектором `.select2` — а по нему select2 в своём
обработчике «клик мимо списка» ищет **свой контейнер**:

```js
var n = $(event.target).closest('.select2');
$('.select2.select2-container--open').each(function () {
    if (this != n[0]) $(this).select2('close');   // закрыть чужие списки
});
```

`closest('.select2')` находил не контейнер, а само поле, `this != n[0]`
оказывалось истиной — и select2 закрывал только что открытый собственный
список. Всё происходило внутри одного события `mousedown`: список открывался и
закрывался за 3 мс, со стороны — «не реагирует». Программное открытие
(`.select2('open')`) работало, потому что там нет `mousedown`, — поэтому сбой и
не ловился беглой проверкой.

**Починка** — в общем мосте `public/metronic/js/osmo-metronic.js` (там же живёт
обвязка select2 для попапов из v20): после инициализации лишний класс `select2`
снимается с видимого поля. Контейнер свой класс сохраняет — его ставит сам
плагин, и обработчик по-прежнему находит открытые списки. Одна правка закрывает
все места сразу: попапы спецификации, договора, оплат, фильтр дашборда и
страницы, где select2 поднимают по `$(".select2")` (компании, отчёты, меню).

**Заодно** в тех же попапах исправлен `dropdownParent: $(".modal .modal-content")`
— он указывал на **первую** модалку документа, а не на свою (14 мест в 7 файлах).
Сбоя это не вызывало, пока на странице нет второй модалки, но идиома проекта —
`$("#staticBackdrop")`.

### 5. Карточка проекта: оплаты по каждой спецификации

В таблицу спецификаций добавлена колонка «Оплаты» — ячейка повторяет таблицу
договоров на карточке партнёра (иконка состояния, план → факт, просрочка в днях,
план → факт по сумме). Колонка «Сумма» теперь считается по плановым платежам
(`payments.amount_plan`), как на карточке партнёра, а не по полю
`contract_specifications.amount`, которое обычно пустое.

Платежи подгружаются вместе со спецификациями (`with(['…', 'payments'])`), без
N+1.

### 7. Список КП: привязка сделки без перезагрузки (ТЗ п.6)

Было: `deal_done()` в попапе привязки делал `location.reload()`, и со второй
страницы списка сбрасывались и страница, и сортировка.

Стало: ячейка «Сделка» помечена `data-deal-cell` (группа КП), попап после
изменения зовёт `window.deal_changed(group)`, если страница его объявила.
Список КП объявляет его и перерисовывает **одну ячейку** — через новый
`GET /api/proposal/deal/cell/{proposal}` (`api.proposal.deal_cell`), который
отдаёт разметку того же компонента. Страница не перезагружается, таблица не
обновляется целиком. Остальные страницы (карточка КП, сводная карточка)
работают как раньше — там остаётся перезагрузка.

### 8. Вкладки «Проекты» и «Архив проектов» на карточке партнёра

Те же вкладки, что в реестре, но в срезе партнёра. Вся обвязка уже была в v24
(`PartnerController::TAB_PREFIX`, режимы в `_tab.blade.php`) — добавлены сами
вкладки, панели и загрузка.

Сделка с архивным проектом остаётся в реестре — в архив уходит проект, а не
сделка. Проверено: сделки 751 и 747 (единственные архивные проекты локальной
базы) видны в `/bitrix/deal?has_proposal=all` и на вкладке «Сделки Битрикс»
карточки партнёра.

### 9. Числа в скобках у вкладок реестра

`CrmDealRegistryService::counts()` — одним лёгким запросом (только id сделок)
считает все три вкладки. Число показывает то, что вкладка покажет **по клику**,
то есть с её собственными значениями по умолчанию: у «Сделок» реестра это сделки
без привязанного КП, у вкладок проектов — все. Текущий фильтр пользователя в
счёт не идёт — вкладки на него не ссылаются. Пояснение висит подсказкой на
самой вкладке.

Те же числа стоят у вкладок карточки партнёра — там с умолчаниями карточки
(«есть КП» не важно).

### 10. Сводная карточка сделки: только спецификации этого КП

`DealChainService::specifications()` брал **все** спецификации договоров, в
которых нашлась хоть одна спецификация этого КП, — то есть почти все
спецификации партнёра. Теперь отбор идёт по `contract_specification_proposals`
для группы КП. На `/deal-card/862b74eb-…` было 8 строк, стало 2 — ровно те, что
прикреплены. Это меняет и деньги в шапке карточки, и шаги цепочки: они считались
по чужим спецификациям.

### 11. Фильтр «Заказчик» во вкладке сделок

В Битриксе конечный заказчик — текстовое поле сделки (`uf_crm_1717755645`),
а не справочник, поэтому список значений собирается из самих сделок области:
на карточке партнёра — только заказчики его сделок, на реестре — все.
`CrmDealRegistryService::customers(?Partner)` + поле `customer[]` в фильтре;
отбор уезжает и в выгрузку Excel, и в адрес страницы (то есть переживает F5).

Проверено на партнёре 839: в списке 10 заказчиков, отбор «ЦОДД» даёт 8 строк,
«ВСМ-400» — 3, «ЦОДД + Метрополитен» — 10. Те же числа в базе.

## Руками

Ничего. Патч ставится `git pull` + `php artisan optimize:clear`.

Файл `public/metronic/js/osmo-metronic.js` под git (коммит b0fb1af взял свои

отдаётся статикой.

531cbba, то есть v21–v23 часть 1):
