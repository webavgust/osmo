# patch v36 — AJAX API без сессии: ответ «не авторизован» вместо 500

Ставится поверх v35. Главная правка — в `app/Http/Middleware/AjaxApi.php` (middleware `ajax.api`,
через него идут все `/api/...` модулей и пульс страницы `spider.tick`); вдогонку — три обработчика
в шаблонах, которые на ответ «не авторизован» показывали «Это успех!».

## Что было

Для запроса без пользователя в сессии middleware пытался войти по токену:

```php
$user = UserRepository::getByToken($request->input('_token'));
Auth::loginUsingId($user->id);
```

`UserRepository` не импортирован (ищется как `App\Http\Middleware\UserRepository`), а метода
`getByToken` нет нигде в проекте — ветка сломана с первого коммита. Любой AJAX-запрос без сессии
(гость, истёкшая сессия, выход в соседней вкладке, `_token=undefined`) падал с **500**
`Class "App\Http\Middleware\UserRepository" not found`. Так возникал 500 от `/api/settings/set`
в аудите дизайна 25.09.2026 (v35).

## Что стало

Без сессии — тот же ответ, что middleware уже давал при чужом токене: `{"error": "auth"}` (HTTP 200).
Пустой `_token` — по-прежнему 403, сравнение с `ajax_token` пользователя — как было.

**Входа по одному токену нет — решение владельца 25.09.2026.** Он ни разу не работал, а включать его
не стали: `ajax_token` ходит в адресах запросов (попадает в логи сервера) и живёт до выхода из системы,
то есть стал бы бессрочным ключом. Неиспользуемый `AjaxToken::check()` (поиск пользователя по
токену) оставлен как был.

Почему 200, а не 401: пульс страницы `spider.tick` (оба лейаута, каждые 3 с при видимой вкладке,
60 с при скрытой) в `success` проверяет `response.error == 'auth'` и уводит на форму входа. С 200 это
теперь срабатывает: страница, у которой пропала сессия, через несколько секунд переходит на `/auth`
(раньше — 500 каждые 3 с в консоли, страница оставалась на месте, сохранения молча не проходили).
При 401 ответ ушёл бы в `error`, и переход не случился бы.

## Фронтенд: на 500 никто не опирался

- `public/js/app.js`, `public/js/pages.js`: обработчиков статуса 500, `statusCode`, глобальных
  `ajaxError` / `ajaxSetup` нет; `{error: 'auth'}` проверяет только `spider.tick` в
  `layouts/layout.blade.php` (обе темы).
- Обработчики в шаблонах почти все проверяют флаг ответа (`status == 'success'`,
  `result == 'success'`, `response.success`) — на `{error: 'auth'}` они уходят в свою ветку ошибки.
- Три обработчика показывали «Это успех!», не глядя в ответ (так было и раньше при чужом токене) —
  поправлены в этом же патче, см. ниже.

## Ложный успех в трёх обработчиках (тема Metronic)

> **Снято patch v38 (25.09.2026):** оба шаблона удалены вместе с мёртвыми страницами «Рабочий график» и
> «Привязка аналитика к объектам» (решение владельца). Раздел оставлен для истории; при выкатке v36 + v38
> от правки ничего не остаётся.

`themes/metronic/pub/user/work_calendar.blade.php` — «Сохранить» (`api.users.work_calendar.set`) и
«Скопировать из производственного календаря» (`api.users.work_calendar.copy`);
`themes/metronic/pub/user/analytics_bind.blade.php` — «Сохранить» (`api.users.analytic_bind`).
На `{error: 'auth'}` теперь «Сессия истекла — войдите заново» / «Это провал!», успеха нет, копирование
не перезагружает страницу (иначе сообщение не увидеть). Остальное — как было. Проверка идёт по
`error`, а не по флагу успеха: `work_calendar_set` и `work_calendar_copy` возвращают эхо запроса
(`$request->all()`; в форме только `time[…]` и `date[]`), `analytic_bind` — `{status: …}`.

**Страницы сейчас не открываются — и не из-за этой правки** (решение владельца 25.09: правку оставить):
- «Рабочий график» `/user/{id}/work_calendar` — 500: моделей
  `App\Modules\Pub\UserWorkCalendar\Models\UserWorkCalendar` и `WorkCalendar` нет в git с первого
  коммита. К тому же `work_calendar_show` рендерит `pub::user.work_calendar` — это файл старой темы,
  копия в Metronic не используется (`pub::` идёт мимо темы).
- «Привязка аналитика к объектам» `/user/analytics/{id}` (право `lab_objects_bind`) — контроллер зовёт
  `LabObjectRepository` / `LabMeasureRepository`, вычищенные вместе с кластером прошлого проекта, у `User`
  нет связи `lab_objects()`.
- В меню (таблица `menus`) ссылок на обе страницы нет.

Старая тема (`resources/views/pub/user/work_calendar.blade.php`, строки 182 и 223;
`pub/user/analytics_bind.blade.php`, строка 324) — тот же ложный успех, не менялась.

## Проверка (локально, 25.09.2026)

`POST /api/settings/set` (Anna, user 1; записи настроек у неё нет — база не меняется):

| Запрос | До | После |
|---|---|---|
| cookie + верный `_token` | 200 | 200 |
| cookie + чужой `_token` | 200 `{"error":"auth"}` | 200 `{"error":"auth"}` |
| без cookie + верный `_token` | **500** | 200 `{"error":"auth"}` |
| без cookie + `_token=undefined` | **500** | 200 `{"error":"auth"}` |
| без cookie, пустой `_token` | 403 | 403 |

`POST /api/spider/tick`: с cookie — `{"is_live":true,…}`, без cookie — `{"error":"auth"}`.
В браузере (WebKit): открытая `/partners`, cookie стёрты — следующий пульс получил `{error:'auth'}`,
страница перешла на `/auth`.

Обработчики из двух шаблонов — вне страницы (страницы не открываются, см. выше): скрипты вырезаны из
шаблонов, jQuery и toastr — заглушки, `success` вызван с разными ответами. Скрипты разбираются без
ошибок.

| Обработчик | Обычный ответ | `{error:'auth'}` | Пустой ответ |

| график: «Сохранить» | «Даты сохранены!» | «Сессия истекла…» | «Даты сохранены!» |
