# Патч A — статус КП, связь со сделкой Битрикса, виджет продления лицензий

Первый из четырёх патчей по новому функционалу. Закладывает то, без чего
не считается остальная аналитика: статус КП и связь КП со сделкой.

Устанавливается поверх патчей v1–v5. **Вёрстка размещена** — компоненты уже
стоят на дашборде, в карточке КП и в списке КП.

## Где что появилось

### Дашборд `/bitrix/dashboard`

Виджет «Продление лицензий» встал седьмым в ряду показателей. Ряд переведён
с `col-xl-2` на `col-xl` — семь равных колонок вместо шести, остальные виджеты
не тронуты. На планшете по три в ряд, на телефоне по два.

Виджет показывает общее число истекающих лицензий, разбивку по горизонтам
30 / 60 / 90 дней, счётчик уже истёкших и оценку суммы продлений. Клик открывает
попап со списком и переключателями горизонта.

### Карточка КП `/proposals/detail`

Под названием КП — два бейджа: статус (кликабельный, открывает попап смены)
и сделка Битрикса. Бейдж сделки показывает `#ID`, если привязана, или
«Нет сделки» — клик в обоих случаях открывает попап поиска.

В меню действий (три точки) добавлены «Изменить статус» и «Сделка Битрикс24»
после разделителя.

### Список КП `/proposals`

Колонка «Статус» между «Дата КП» и «Изменено». В ячейке — бейдж статуса
(клик открывает попап), под ним причина проигрыша и номер привязанной сделки,
если есть.

В фильтре два новых блока: статусы (чекбоксы, множественный выбор)
и «Сделка Битрикс24» — привязана / не привязана / неважно. Сброс фильтра
очищает и их.

## Что внутри

### 1. Статус КП

Статус лежит на строке `proposals`, но принадлежит **группе** — КП целиком со
всеми итерациями. `ProposalStatusService::set()` пишет во все строки группы,
поэтому любой запрос к любой итерации возвращает актуальный статус без join.

Семь статусов (`ProposalStatus`): в работе, отправлено, на согласовании,
выиграно, проиграно, заморожено, отменено. Три последних требуют причины
(`ProposalLostReason`): дорого, ушли к конкуренту, нет бюджета, сроки,
не хватило функционала, отпала потребность, не отвечает, наше решение, другое.

Готовые методы для отчётов:

```php
ProposalStatusService::counters();     // ['won' => 12, 'lost' => 3, ...]
ProposalStatusService::conversion();   // 42.9 — процент выигранных среди завершённых
Proposal::latestIteration()->status('won')->get();
```

Существующим КП миграция ставит `in_work`. В SQL-файле есть закомментированные
запросы, чтобы проставить `sent` по дате отправки и `won` по подписанному
договору — включите, если согласны с логикой.

### 2. Связь КП ↔ сделка Битрикса

Связь 1:1 на уровне группы КП. Уникальность проверяет `ProposalDealService`:
привязать занятую сделку нельзя, в ошибке указано, к какому КП она относится.

Поиск рассчитан на 700+ сделок:

* поиск идёт **в БД**, не в памяти — `LIKE` по названию, компании и конечному
  заказчику (`uf_crm_1717755645`), при вводе только цифр — точный поиск по ID;
* несколько слов — каждое должно найтись хотя бы в одном из полей;
* фильтры: менеджер (`assigned_by`), стадия (`stage_name`), «только свободные»;
* при открытии попапа поиск **предзаполняется названием компании из КП** —
  чаще всего нужная сделка находится сразу;
* живой поиск с задержкой 350 мс, выдача ограничена 50 записями;
* занятые сделки помечены бейджем «занята» и по умолчанию скрыты.

В выдаче видно: ID, название, компания, конечный заказчик, менеджер, стадия, сумма.

### 3. Виджет продления лицензий

`LicenseRenewalService` считает по `license_keys.active_to`: горизонты 30/60/90
дней, отдельно уже истёкшие (показываются 30 дней после истечения — их ещё можно
вернуть), оценка суммы.

**Про оценку суммы.** Отдельной цены продления в базе нет, поэтому берётся сумма
спецификации, по которой был выдан ключ, делённая на количество ключей в ней.
Это лучшая доступная оценка, но не точная цена. Появится отдельное поле —
поправлю расчёт в одном методе `renewalAmount()`.

## Проверка после установки

- [ ] дашборд открывается, семь виджетов в ряд не разъехались
- [ ] виджет лицензий показывает число, попап открывается, переключатели 30/60/90 работают
- [ ] в карточке КП видны бейджи статуса и сделки
- [ ] смена статуса сохраняется, для «Проиграно» требует причину
- [ ] попап сделки открывается с подставленным названием компании
- [ ] поиск сделок находит по названию, по ID, фильтры по менеджеру и стадии работают
- [ ] привязка и отвязка сделки работают, занятую сделку привязать нельзя
- [ ] в списке КП есть колонка «Статус», бейдж кликается
- [ ] фильтр по статусу и по наличию сделки фильтрует, сброс очищает
